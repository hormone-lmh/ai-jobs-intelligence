# AI 岗位情报分析系统 — 技术方案

版本：v2.0（D1、D2 已决议，记录见 §10）
日期：2026-11-11
定位：单人、本机运行、本地数据，不做多用户与云端部署

---

## 0. 结论摘要

原方案的方向是对的：本地库 + 规则词典 + 交互页面 + 口径可追溯。以下三处建议修正，其中第一条是硬约束，不改会导致阶段 2 之后全面返工。

| 编号 | 原方案 | 建议改为 | 依据 |
|---|---|---|---|
| C1 | BOSS 数据接入是「核心入口」 | **维持为核心路径**（D1：按你的决定）。但文件导入保持完整可用，作为采集失效时的同口径兜底；采集实现限定为"你本人登录态 + 低频可视读取"，不实现任何绕过手段 | 站点 robots.txt 明确禁止带查询参数的抓取，见 §1.2；协议与账号风险如实标注，不粉饰 |
| C2 | Python 后端（默认本机已有） | 保留 Python，但**先安装到本机**，且不与 Doubao 运行时共用 | 本机无系统级 Python，仅有 agent 沙箱运行时，见 §1.1 |
| C3 | 六个页面一起做 | 阶段 2 只做 3 个页面（总览 / 岗位探索 / 数据与任务），阶段 3 补其余 3 个 | 前端骨架一次成型，不返工；但先让闭环跑通 |

## 1. 环境与外部条件核对（实测，非推断）

### 1.1 本机工具链

| 项 | 实测结果 | 对方案的影响 |
|---|---|---|
| 操作系统 | Windows，PowerShell 7.6.4 | 启动脚本用 `.ps1`，不用 `.bat` |
| Node.js | v24.15.0（`C:\Program Files\nodejs`，系统安装，真实可用） | 前端无需额外安装 |
| Git | 2.53.0（`D:\study\Git\cmd`） | 可用于版本管理，非必需 |
| Python | **本机无系统安装**。`py` 启动器、`LOCALAPPDATA\Programs\Python`、Microsoft Store 别名均不存在 | **后端必须先装 Python**（D2） |
| 沙箱 Python | 3.13.16，位于 `...\sandbox_runtime\bases\772984f6...\python` | 不可作为长期运行环境：base 目录按运行时版本哈希命名，升级即失效 |
| winget | 未安装 | 装 Python 需走官方 installer 或 Microsoft Store |
| 磁盘 | F: 剩余 184.7 GB，C: 剩余 38.0 GB | 数据与依赖全放 F:，不占 C: |

结论：**Node 侧零成本，Python 侧需要一次安装动作**。这是阶段 0 的前置，不解决则阶段 2 无法启动。

### 1.2 目标站点可达性与允许范围（本机单次请求实测）

可达性：DNS 解析正常（多 A 记录），443 端口连通，`https://www.zhipin.com/` 返回 200、531 KB、含完整 `<title>`。**说明网络层面没有障碍**，问题不在"能不能连上"。

允许范围：`https://www.zhipin.com/robots.txt` 返回 200，与采集相关的原文如下（逐字引用）：

```
User-agent: *
Disallow: /*?query=*
Disallow: /*?ka=*
Disallow: /*?sid=*
Disallow: /*?city=*
Disallow: /*?experience=*
Disallow: /*?salary=*
Disallow: /*?degree=*
Disallow: /*?key=*
Disallow: /*?page=*
Disallow: /*?*
Disallow: /job_detail/l*.html
Disallow: /web/geek/recommend*
```

关键判定：

1. `Disallow: /*?*` 是兜底规则，含义是**任何带查询串的 URL 都不允许抓取**。而 BOSS 的关键词搜索、城市/经验/学历/薪资筛选、翻页，全部依赖查询参数（`?query= &city= &experience= &page=`）。按该协议，**筛选式自动采集不在允许范围内**，且这不是频率高低能解决的问题——低频访问同样落在 `Disallow` 之内。
2. `Disallow: /job_detail/l*.html` 直接覆盖列表页形态的职位详情。
3. 你举例的 `https://www.zhipin.com/zhaopin/a5c8bfc9d243469d1nd73Nu7FQ~~/` 是路径式 SEO 聚合页，不带查询串，robots 未逐条禁止。但它是**面向搜索引擎的缓存型落地页**，本身不代表实时在招岗位，也不能按关键词/城市重新组合。把它作为数据源，等于把"历史索引"当"当期需求"，正是你在方案里担心的那个误判。
4. 由此，"低频访问"与"取得授权"是两件事，你的判断成立，而且比预估更严格：**连授权的基础（robots 允许）都不具备**。

因此本系统的数据来源按下列优先级组织（C1）：

| 优先级 | 入口 | 说明 | 状态 |
|---|---|---|---|
| P0 核心路径 | BOSS 登录态低频采集 | 由你本人完成登录，系统复用浏览器 profile 读取你账号可见的搜索页与详情页；单次低频、串行、有日上限；不做并发与轮换 | 主路径，阶段 1 必须先验证 |
| P1 兜底入口 | 文件导入（CSV / Excel / JSON） | 数据由你在合规渠道取得后导入；只负责解析、去重、分析。**采集失效时系统仍可完整使用** | 一直可用，且与 P0 同口径 |
| P2 补充入口 | 手动文本录入 | 粘贴 JD + 来源链接 + 来源说明，一键提取 | 一直可用 |
| P3 明确不做 | 绕过类手段 | 验证码破解/代答、风控规避、cookie 伪造与共享、代理池与 IP 轮换、频率限制规避 | 不实现，不预留开关 |

P1 不是"备选"，而是 P0 的**同口径兜底**：两者写入同一张表、走同一套去重与技能提取，保证采集失效期间统计口径不发生跳变。这是"数据缺失不被读成需求下降"的前提，也是本方案要求两条通道都实现的原因。

**本方案不包含、也不会实现**：绕过登录或验证码、伪造/复用 cookie、代理池、请求频率规避、破解风控。这些不属于"可行性优化"，属于另一类问题。

### 1.3 由此确定的验收前提

阶段 1 的验收标准（按 D1 调整）：

> ① 验证"登录态 + 低频可视采集"链路：列表页字段与详情页 JD 能否稳定取到；登录过期、验证弹窗、频控页、字段缺失分别如何表现；失败能否被识别，而不是静默产出空数据。
> ② 产出三通道（采集 / 导入 / 手动）的字段覆盖矩阵，写明每条通道拿得到、拿不到哪些字段。
> ③ 记录该来源的 robots 状态与账号风险，作为"来源健康度"的初始基线。
> 若 ① 在 3 个工作日内做不到"可重复、失败可识别"，则 P0 降级、改由 P1 承担核心，**阶段 2 不因此推迟**。

三个产出都写进 `docs/01-数据可行性报告.md`。"大概能抓到"不算结论。

### 1.4 采集实现形态（P0 的具体做法）

三种形态，采用第一种：

| 形态 | 做法 | 判定 |
|---|---|---|
| A 持久化浏览器 profile（**采用**） | Playwright 启动独立浏览器，profile 落 `data/browser_profile/`。你首次手动登录一次，之后复用该 profile 的会话读取页面 | 会话来自你自己的浏览器登录，不是代码伪造；读取的是你账号本来就能看到的页面 |
| B 驱动你当前的 Chrome | 复用已登录的浏览器实例 | 需要你在场，适合调试与首次验证，不适合无人值守定时 |
| C 纯 HTTP + 手工搬 cookie | 复制 cookie 直接发请求 | **不采用**：等价于伪造会话，且最易触发风控 |

形态 A 写进代码的硬约束（不是建议）：

1. **串行单会话**，不并发。请求间隔下限可配置，默认 ≥ 10 秒；每日采集轮次上限默认 1 次。
2. 命中登录页、滑块、短信验证、异常频控页 → **立即暂停任务**并置 `coverage_gap(reason=auth_expired|challenge)`，等你人工处理后恢复。不重试、不换 IP、不改 UA 硬闯。
3. 每次采集无论成败都写 `ingest_batch`：`adapter_name, session_profile, page_url, captured_at, http_status, result`。
4. 页面结构变化导致字段解析失败 → 记 `parse_error`，原始响应落 `data/raw/<batch_id>/`，供修复解析规则时回溯。**绝不把解析失败写成空字符串入库**，否则"没解析到"会被读成"岗位没这个要求"。

### 1.5 实测结论：P0 不可用（2026-11-11）

阶段 1 实测三条路径：

| 路径 | 结果 |
|---|---|
| Playwright `launch()` + 本机 Chrome 157 | 页面被置为 `about:blank`（39 字符、卡片 0），有头无头一致 |
| 普通 Chrome 手动访问 | **正常**，有内容，稳定在职位列表页 |
| Playwright `connect_over_cdp()` 接管 | 页面被重置并进入导航循环，DOM 读不到 |

所以不是平台封杀浏览器，也不是网络问题：**只要程序接管浏览器，会话就被重置**。完整证据见 `docs/01-数据可行性报告.md` §4。

据此按 §1.3 降级：

- `zhipin` 适配器置 `enabled: false` / `role: disabled`，只保留接口位（`config/sources.yaml`）。
- 主路径改为"**用户自取内容 + 本地解析**"：快照文件导入 / 整页粘贴 / CSV-Excel 导入。
- 不研究如何通过指纹识别。那属于规避风控，成功率不稳定，且与"低频即合规"是两件事。

该结论不改变阶段 2 的启动条件（§1.3 已预留），但改变其数据前提：

1. 每条岗位必须带 `source_channel`（`snapshot` / `manual` / `file`）。
2. 趋势图不得跨 `source_channel` 连线。
3. "某日无数据"多数情况代表"你没导入"，页面顶部必须写明，不能放脚注。

## 2. 统计口径定义

原则：**每个数字都能回答"分母是什么、样本从哪来、什么时候的"**。下表中"可用岗位"= 有非空 `jd_text` 且 `jd_text` 长度 ≥ 50 字符的去重岗位。

| 用户问题 | 系统口径 | 精确公式 | 边界处理 |
|---|---|---|---|
| 有多少岗位 | 筛选范围内已搜集并去重的职位发布数 | `count(distinct posting)` 满足当前筛选 | 与平台全量无关，页面必须标注"本地样本" |
| 招聘多少人 | 仅统计明确填写的名额 | `sum(headcount_int)`，`headcount_int` 仅当原文可直接解析为整数时写入 | "若干""N 人以下""储备"→ `headcount_raw` 保留原文，`headcount_int=NULL`，只计数不求和 |
| 哪些公司在招 | 最近成功核验仍在招的公司 | `company` 下存在 `status=active` 且 `last_verified_at >= now - 30d` 的岗位 | 同时显示核验时间；超期标"待核验"，不标"在招" |
| 最新要求 | 最近一次抓取的要求 + 与上次记录的差异 | 取 `job_snapshot` 最新一条，与 `prev_snapshot_id` 做字段级 diff | 差异仅在有前后两份快照时展示 |
| 需求是否上涨 | 同口径下本地样本变化 | 同一 `scope_fingerprint` 下的 `count(distinct posting)` 按 `first_seen_at` 归期 | 口径变更即断线，见 §2.3 |

### 2.1 技能类指标

| 指标 | 公式 | 说明 |
|---|---|---|
| 技能提及率 | `提及该技能的去重岗位数 ÷ 可用岗位数` | 分母固定为"可用岗位"，避免无 JD 的岗位稀释分母 |
| 必备占比 | `strength=required 的岗位数 ÷ 可用岗位数` | `required` 判定见 §4.2 |
| 技能组合 | `同时含技能集合 S 的岗位数 ÷ 可用岗位数` | 支持 2–4 个技能，组合数上限在 UI 限制 |
| 门槛分布 | 学历 / 经验 / 岗位类型的构成比 | 分母同上；"不限"单独成类，不并入任何档位 |

所有技能指标必须显示：`分子 / 分母 / 分母中 JD 完整度分布`。

### 2.2 薪资口径

不合并币种与周期，三类分离：

| 类型 | 字段 | 年化条件 |
|---|---|---|
| 月薪 | `salary_unit=month`, `salary_min/max`, `salary_months` | 仅当原文明确"×13薪"等才年化；`salary_months` 为空则 `annualized=NULL` |
| 年薪 | `salary_unit=year` | 直接使用 |
| 实习日薪 | `salary_unit=day` | 不做年化，单列 |
| 面议 / 未给 | `salary_state=negotiable / unknown` | 不进薪资均价，单独计数 |

`annualized_*` 为 NULL 的岗位在薪资对比中**剔除并显示剔除数**，不用 12 薪补空。

### 2.3 口径指纹（防止"数据缺失被读成需求下降"）

```
scope_fingerprint = sha256(
    sorted(city_list) || sorted(keyword_list) || direction_ids ||
    source_channels || degree_filter || experience_filter
)
```

规则：

1. 趋势图只连接**同一 fingerprint** 的数据点；跨 fingerprint 直接断开，并标注"口径变更（旧→新）"。
2. 某日无成功采集 → 该日写 `coverage_gap` 记录，图上渲染为灰色空档，**不渲染为 0**。
3. 每个数据点必须携带 `有效样本量`，样本量 < 20 时该点降级为空心点并提示"样本不足"。
4. 同一岗位的"消失"不计入下降，只有 `closed_confirmed` 才计入。

## 3. 数据模型

SQLite + SQLAlchemy 2.0 + Alembic。WAL 模式；`data/jobs.db`。JD 全文检索用 SQLite FTS5（`jd_fts` 虚拟表），避免全表 LIKE。

### 3.1 表结构

**job_posting**（岗位当前态）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | uuid4 |
| platform | TEXT | `zhipin` / `import` / `manual` / `other` |
| platform_job_id | TEXT NULL | **首选去重键** |
| fingerprint | TEXT | `sha256(company_norm\|title_norm\|city_norm)`，无平台 ID 时的备选键 |
| duplicate_state | TEXT | `unique` / `suspect` / `merged` / `merged_into:<id>` |
| url | TEXT NULL | 来源链接 |
| source_channel | TEXT | `file_import` / `manual` / `browser_assist` |
| source_note | TEXT NULL | 来源说明（导入批次、文件名、你填写的备注） |
| title / title_norm | TEXT | 岗位名 / 归一后名称 |
| company_id | TEXT FK | → company |
| city / city_norm / district | TEXT | 城市归一（"上海·浦东"→ city=上海, district=浦东） |
| salary_raw | TEXT | 原文薪资串，永不丢 |
| salary_min / salary_max | INTEGER NULL | 归一数值（月/年/日 由 unit 决定） |
| salary_unit | TEXT NULL | `month` / `year` / `day` |
| salary_months | INTEGER NULL | 薪数 |
| salary_state | TEXT | `range` / `fixed` / `negotiable` / `unknown` |
| headcount_raw / headcount_int | TEXT / INTEGER NULL | 招聘人数 |
| degree_raw / degree_level | TEXT / INTEGER NULL | 0 不限 / 1 大专 / 2 本科 / 3 硕士 / 4 博士 |
| experience_raw | TEXT | 原文 |
| experience_min_years / experience_max_years | REAL NULL | 归一；NULL=不限 |
| job_type | TEXT | `intern` / `campus` / `experienced` / `unknown` |
| job_type_confidence | REAL | 由标题关键词与经验字段推断的置信度 |
| jd_text | TEXT | 完整原文 |
| jd_hash | TEXT | 内容哈希，用于变更检测 |
| data_completeness | REAL | 0–1，必填字段加权得分 |
| status | TEXT | 见 §3.3 |
| miss_count | INTEGER | 连续未命中次数 |
| first_seen_at / last_seen_at / last_verified_at | DATETIME | 三个时间语义严格区分 |
| published_at | DATETIME NULL | **仅来源明确提供时写入**，否则 NULL，不用采集时间顶替 |
| created_at / updated_at | DATETIME | |

**job_snapshot**（每次采集/导入一份，用于"要求变化"）

`id, posting_id, captured_at, jd_hash, jd_text, salary_raw, degree_raw, experience_raw, status_at_capture, prev_snapshot_id, changed_fields(JSON), change_type(new|unchanged|updated|vanished)`

**company**

`id, name, name_norm, industry(NULL), size(NULL), city(NULL), first_seen_at, last_seen_at, watch_flag, note`

**skill_taxonomy**（词典）

`id, canonical_name, aliases(JSON), category, direction_tags(JSON), is_active`

**skill_mention**（证据链，一行一条）

`id, snapshot_id, posting_id, skill_id, match_type(rule|llm|manual), strength(required|preferred|involved|unknown), section(requirement|responsibility|company_intro|unknown), evidence_text, span_start, span_end, confidence`

**ingest_batch**（导入/采集批次，用于幂等与追溯）

`id, channel, started_at, finished_at, params(JSON), total_rows, inserted, updated, skipped_dup, failed, error_log_path`

**coverage_gap**

`id, scope_fingerprint, date, reason(auth_expired|network|parse_error|no_source|user_paused), detail`

### 3.2 去重规则

1. 有 `platform_job_id`：`(platform, platform_job_id)` 唯一。命中即更新，不新增。
2. 无平台 ID：`(platform, fingerprint)` 命中 → 视为同一岗位，更新并记快照。
3. `fingerprint` 命中但 `url` 不同，或 `title_norm` 相似度 ≥ 0.9 且 `company_norm` 相同 → `duplicate_state=suspect`，**保留两条，不自动合并**，在"数据与任务"页列"疑似重复"待你确认。
4. 合并只由人工触发，合并后保留 `merged_into` 指向，原始记录不删。

### 3.3 状态机（"没搜到 ≠ 下架"）

```
导入/采集命中         → active
本轮未命中            → 状态不变，miss_count += 1
miss_count >= 3 且跨度 >= 3 天 → inactive_suspected（待核验）
详情明确显示已关闭/下线 → closed_confirmed
人工确认关闭          → closed_confirmed（note 记来源）
```

不允许"未命中即置为关闭"。`inactive_suspected` 在统计中仍计入"历史岗位"，但不计入"在招岗位"。

## 4. 技能提取设计

### 4.1 词典（`config/taxonomy.yaml`）

结构示例：

```yaml
directions:
  - id: llm_app
    name: 大模型应用开发
  - id: llm_train
    name: 大模型算法与训练

skills:
  - canonical: RAG
    aliases: [RAG, 检索增强生成, Retrieval-Augmented Generation, 检索增强, 知识库检索增强]
    direction: [llm_app]
    category: technique
    risk: ["RAGFlow", "RAGAS"]        # 排除误匹配
  - canonical: 强化学习
    aliases: [强化学习, RL, Reinforcement Learning, RLHF, 人类反馈强化学习]
    direction: [llm_train, llm_infra]
    category: technique
```

匹配规则：

1. 别名按长度降序匹配，先长后短（"检索增强生成"先于"检索增强"）。
2. 拉丁别名按词边界 `\b` 匹配并排除 `risk` 词表。
3. 命中后取**所在整句**为 `evidence_text`（截断 200 字符），记录 `span`。
4. 否定检测：句中 `不要求/无需/非必须/不需要` 出现在技能前 8 字符内 → 该次命中丢弃，记 `negated=true` 供审计。

### 4.2 强度判定

| strength | 判定条件 |
|---|---|
| required | 位于"任职要求/任职资格/岗位要求/你需要具备"等段落，且与 `必须/精通/熟练掌握/深入理解/至少/要求` 共现；或该句为纯技能枚举（无动词短语） |
| preferred | 与 `优先/加分/更佳/有…经验者优先/了解者优先` 共现 |
| involved | 仅出现在"岗位职责/工作内容/你将负责"段落，或与 `了解/接触/参与` 共现 |
| unknown | 段落边界无法识别（短 JD、无小标题） |

段落识别：先按小标题正则切段（`岗位职责|工作内容|职位描述|任职要求|任职资格|岗位要求|我们希望你|加分项|公司介绍|关于我们`），无小标题则整篇 `unknown`。LLM 可用时，仅用于**段落归类**与**词典未覆盖的候选技能发现**，两项都必须返回可定位的原文 span，无法定位即丢弃。

### 4.3 约束

- 大模型只处理已取得的 JD 文本；不参与任何数量、趋势、薪资计算；不允许补全缺失字段。
- 无大模型密钥时，`match_type=rule` 全链路可用，统计结果口径不变（仅召回率下降，需在页面标注"未启用语义增强"）。
- 每条技能数字在 UI 上必须能向下追溯到 `skill_mention → snapshot → 原文句子`，三次点击内到达。

## 5. 技术选型

| 模块 | 选型 | 决策说明 |
|---|---|---|
| 后端 | Python 3.12 + FastAPI + Pydantic 2 | 3.12 而非 3.13：pandas/numpy/pyarrow wheel 覆盖更全 |
| 数据库 | SQLite（WAL）+ SQLAlchemy 2.0 + Alembic + FTS5 | 单人单机足够；FTS5 解决 JD 全文检索 |
| 数据处理 | pandas 2.x | 只用于导入清洗与聚合，不写回 ORM 之外 |
| 技能提取 | 纯 Python 规则引擎（`re` + 词典）+ 可选 LLM | 不引入 spaCy/transformers，避免模型下载与体积 |
| 前端 | React 18 + TypeScript + Vite + Ant Design 5 | 不用 Next.js：无 SSR 需求，纯本地 SPA 更轻 |
| 图表 | ECharts 5 | 同原方案 |
| 采集执行 | Playwright（Python）+ 持久化浏览器 profile | 见 §1.4 形态 A；直接驱动本机已装 Chrome，不额外下载 Chromium（省约 300 MB） |
| 任务调度 | APScheduler 3.x（独立进程） | 4.x 尚不稳定；调度进程与 API 进程分离，避免阻塞请求 |
| 数据源适配器 | 每源一个独立模块，统一 `BaseAdapter` 接口 | 见 §1.2；`zhipin` 为主路径，`file` 与 `manual` 常开 |
| 依赖管理 | venv + requirements.txt（锁定版本） | 不引 uv/poetry，减少额外安装 |
| 日志 | loguru → `data/logs/` | 按天轮转，导入/采集错误单独落盘 |

明确不做：Redis、Celery、向量数据库、Docker、PostgreSQL（数据量增长后再议）。

## 9. 已知限制（须在 README 与页面注明）

1. 本系统统计的是**本地样本**，不是平台全量。任何数字都不能表述为"市场共有 N 个岗位"。
2. 关机期间不采集。重启后补采只覆盖当时的页面状态，不补历史空缺 → 必然产生 `coverage_gap`，图上必须可见。
3. BOSS 自动采集为主路径，但不提供任何绕过手段（§1.2、§1.4）。采集能否持续取决于平台风控与页面结构变化，与协议本身的冲突见第 7 条。只使用导入时，系统功能完整，仅"自动刷新"能力缺失。
4. 无平台职位 ID 的数据源，去重依赖 fingerprint，会有误判；一切 `suspect` 交人工。
5. `published_at` 多数来源不提供，故"发布时间"维度不可靠，趋势一律按 `first_seen_at` 归期。
6. 大模型增强为可选项。未启用时召回率偏低，页面需标注，避免与启用后的数字直接比较。
7. P0 采集与该来源当前协议不一致（robots `Disallow: /*?*`）：账号可能被限制，页面结构或风控策略变化会导致采集中断。系统会把"来源健康度"与 `coverage_gap` 显式展示，但**不能消除**这些风险。只用 P1 导入时，分析功能不受影响。
